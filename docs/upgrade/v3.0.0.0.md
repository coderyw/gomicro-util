# v3.0.0.0：租户命名与自动续约锁

> 返回 [README](../../README.md)。

## 租户格式配置

`TENANT_NAME_CASE` 默认 `lower`，可选 `upper`、`original`；配置值可写成 `LOWER` 或带首尾空白。应用应沿用启动时的 `env.SyncEnv()` 校验流程，非法值会返回配置错误。`env.SetTenantNameCase()` 仅用于启动配置或测试，不能在服务运行中切换模式。

本次已确认现有租户均为小写，默认配置保持既有资源名不变，无需迁移。仅格式化租户段，不改变数据库业务名称、Redis key 后缀、Kafka topic 后缀、对象路径、Cron 锁名结构或原始 ctx；空租户和 `TENANT_FALLBACK` 行为保持不变。显式改为 `upper` 会改变资源名称，不能把它当作无影响的运行时开关；`original` 保留传入租户名称。

覆盖 MySQL、Redis、Kafka、S3/OBS storage 组件、本地缓存、Redis 同步任务和定时任务。RabbitMQ 与旧 `object-storage` 接口继续透传调用方资源名，未增加自动租户隔离，使用方需通过命名、连接或其他方式保证隔离。

## Redis 锁生命周期与超时

自动续约锁在请求 ctx 取消后仍会继续续约，直到业务 `do()` 返回或 panic，随后停止续约并执行带持有者校验的解锁。不会因为请求取消而提前释放锁。业务应使用原 ctx 响应取消并最终退出；若 `do()` 永不退出且 Redis 可正常续约，锁会持续被持有。Redis 故障或续约失败仍可能导致锁过期，不能把续约视为绝对互斥保证。

直接使用底层 `RenewalLock` 的调用者仍负责选择 ctx 和调用返回的停止函数；自动包装器通过 `context.WithoutCancel` 实现上述业务生命周期。

全局 `ContextTimeoutEnabled` 保持关闭，不改变其他 Redis 命令原有 deadline 处理方式。解锁使用独立清理 ctx，保留租户与链路信息；其 2 秒 deadline 可限制连接池/重试等待，但网络 I/O 仍遵循客户端读写超时，不能承诺总耗时严格为 2 秒。
